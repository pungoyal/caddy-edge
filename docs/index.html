A hardened HTTPS edge for one Docker host.

Caddy, kept in git and deployed by GitHub Actions. Each application is a four-line file, and adding one is a form. A config Caddy rejects never replaces the one that is serving.

What every site gets

One policy, imported by name. Read it in the Caddyfile, where every line says why.

Sent to the browser

  • Strict-Transport-Security
  • X-Content-Type-Options
  • Content-Security-Policy *
  • Referrer-Policy *
  • Permissions-Policy *
  • Cross-Origin-Opener-Policy *

Removed from responses

  • Server
  • X-Powered-By
  • Via
  • X-XSS-Protection

Stripped from requests

  • X-Real-IP, X-Client-IP
  • CF-Connecting-IP, True-Client-IP
  • Forwarded, X-Forwarded-Port, -Prefix, -Server
  • X-Original-URL, X-Rewrite-URL

Kept out of logs

  • Authorization, Proxy-Authorization
  • Cookie, Set-Cookie
  • Grafana token headers
  • ?token, ?access_token, ?api_key, …

* The document policy has exactly one owner per site. import hardened and the edge writes it: frame-ancestors, object-src 'none', base-uri 'self'. import hardened-app-policy and the application's own passes through untouched. Never both, so an origin never sends two policies that disagree.

Certificates
Obtained and renewed by Caddy for every site file. Nothing to configure.
Unknown hostnames
A request for a name with no site file is aborted, not answered.
Slow clients
Header, body and idle timeouts, and a request-body cap you set per site.
Application restarts
The proxy retries failed connects for 30 seconds, so a request that arrives while a container is being replaced waits instead of getting a 502.
The container
Read-only filesystem, every capability dropped except binding ports, no-new-privileges, memory and CPU limits, admin API on loopback only. No Docker socket.

A deploy that cannot leave you down

CI runs this sequence for real on every change, over SSH against its own runner, failure path included.

  1. Validate. The site files are checked against the Caddyfile, then Caddy is started once with internal certificates. No secrets, so it runs on every pull request.
  2. Ship three things. compose.yaml, .env and caddy/ go to the host over SSH. What was serving is copied to previous/ first.
  3. Reload, not restart. caddy reload applies the config with no dropped connection. The container is recreated only when the Compose file itself changed.
  4. Or put it back. A config Caddy rejects leaves the old one serving. If the deploy does not come up healthy, previous/ is restored and the job fails, with Caddy's log minus the access log.

The host needs Docker and nothing else. No agent, no script, no tool to install: docker compose ps, logs and restart work by hand in the deploy directory.

Adding a site is a form

Whoever can run workflows in your instance repository is an admin. That is the whole access model.

Run it from the Actions tab, the GitHub mobile app or the command line. Every input is matched against a pattern before it becomes config. The run validates, commits to main, optionally creates the DNS record on Cloudflare, and deploys that commit.

gh workflow run site.yml \
  -f action=set -f name=app \
  -f hostname=app.example.com -f upstream=app:3000 -f dns=true

gh workflow run site.yml -f action=remove -f name=app -f dns=true

Anything the form cannot express is a pull request against the site file: the same validation runs, and merging deploys.

Get started

You need a host with a public IPv4 address and a domain whose DNS you control.

  1. Prepare the host. Docker Engine 25 or later with the Compose plugin, a deploy user in the docker group, a directory, a Docker network, and ports 80 and 443 open.
  2. Create a private repository from the contents of examples/instance.
  3. Give it six variables and a deploy key. The host's address, SSH user and host key, the deploy directory, the network name and an ACME contact address.
  4. Run the site workflow to serve your first application.
Read the step-by-step guide

Or call the actions from workflows of your own:

- uses: pungoyal/caddy-edge/actions/deploy@<commit> # v0.1.0
  with:
    sites: sites
    ssh-host: ${{ vars.SSH_HOST }}
    ssh-user: ${{ vars.SSH_USER }}
    ssh-known-hosts: ${{ vars.SSH_KNOWN_HOSTS }}
    ssh-private-key: ${{ secrets.SSH_PRIVATE_KEY }}
    deploy-path: ${{ vars.DEPLOY_PATH }}
    docker-network: ${{ vars.DOCKER_NETWORK }}
    acme-email: ${{ vars.ACME_EMAIL }}
actions/validate
Checks site files and starts Caddy once with internal certificates.
actions/deploy
Ships, reloads, and restores the previous config on failure.
actions/site
Writes or removes one site file from validated inputs.
actions/dns
Sets or deletes a DNS-only Cloudflare A record. Optional.

What it is not

Know before you adopt it.

Not a platform
It does not build or deploy your applications. They are their own Compose projects that join the shared network.
Not a firewall
No rate limiting, no WAF, no bot rules.
Not behind a CDN
Certificates come from HTTP and TLS-ALPN challenges, so the host answers directly and its address is public.
Not multi-host
One Caddy on one host.
Not low-privilege on the host
The deploy user is in the docker group, which is root. Whoever can run your instance's workflows controls the host. The security policy has the full trust model.

If you would rather have applications declare their own routes with container labels, and no repository in between, use caddy-docker-proxy or Traefik. The price is giving the proxy the Docker socket.
