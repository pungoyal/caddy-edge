HTTPS for every app on your Docker server.

Describe an app in four lines and push. It goes live on its own hostname with a certificate and security headers. A mistake in the config never takes your sites down.

Quick start View on GitHub

Free and open source. Built on Caddy and GitHub Actions. Nothing to install on the server but Docker.

How it works

You need a Linux server with Docker and a public IP address, a domain, and a GitHub account.

  1. Your apps run in Docker

    Each one joins a shared Docker network. None of them opens a port to the internet.

  2. You list them in a repository

    One four-line file per app, in a private GitHub repository of your own. Edit a file, or fill in a form.

  3. A push puts them online

    GitHub Actions checks the config and sends it to your server, where Caddy serves every app over HTTPS.

What you get

The same protection for every app, without configuring it per app.

Automatic HTTPS
A certificate for every hostname, obtained and renewed for you. HTTP/3 included.
Security headers
HSTS, clickjacking protection, nosniff, a referrer policy, and browser features such as camera and microphone switched off unless your app asks.
Nothing spoofed
Headers a visitor could forge to fake their address or reach a hidden route are removed before your app sees the request.
Logs without secrets
Passwords, cookies and tokens are stripped from the access log, in headers and in URLs.
No stray answers
A request for a hostname you did not configure is dropped, so scanners learn nothing.
No 502 during restarts
When you redeploy an app, requests wait up to 30 seconds for it to come back instead of failing.
A locked-down proxy
Caddy runs with a read-only filesystem, almost no privileges and no access to the Docker socket.

Added to every response

strict-transport-security: max-age=31536000; includeSubDomains
x-content-type-options: nosniff
content-security-policy: frame-ancestors 'self'; object-src 'none'; base-uri 'self'
referrer-policy: strict-origin-when-cross-origin
permissions-policy: camera=(), microphone=(), geolocation=(), … 14 features off
cross-origin-opener-policy: same-origin-allow-popups

Does your app already send its own Content-Security-Policy? Write import hardened-app-policy 10MB instead, and the last four are left to the app. Every rule is in one commented Caddyfile you can read in five minutes.

Deploys you do not have to watch

Every step below is tested with real deploys each time caddy-edge changes, the failure included.

  1. Checked before it ships. Every pull request and every push is validated by starting Caddy with your config. A typo is caught in GitHub, not on your server.
  2. Applied without downtime. The new config is loaded into the running Caddy. No restart, no dropped connections.
  3. Undone if it fails. If Caddy refuses the config or does not come up healthy, the previous one is put back and the run fails loudly. Your sites keep serving throughout.

To go back to an earlier state yourself, revert the commit. On the server there are three files in one directory and nothing else, so docker compose logs and restart work as you expect.

Add an app without touching a file

A form in your repository's Actions tab. It works from the GitHub mobile app too.

Enter a name, a hostname and where the app listens. The form writes the file, checks it, commits it, creates the DNS record if your domain is on Cloudflare, and deploys. Removing an app is the same form.

# The same thing from a terminal
gh workflow run site.yml \
  -f action=set -f name=blog \
  -f hostname=blog.example.com -f upstream=blog:8080

gh workflow run site.yml -f action=remove -f name=blog

Only people with write access to your repository can run it. Need something the form does not offer? A site file is ordinary Caddy config, so add any directive by hand.

Quick start

Five steps. Commands use the GitHub CLI; everything can also be done on github.com. The full guide has the detail.

  1. Prepare the server

    With Docker Engine 25 or later installed, create the network your apps will share and a directory for caddy-edge. Open ports 80 and 443 in the firewall.

    docker network create edge
sudo install -d -o "$USER" /opt/edge

  2. Put an app on the network

    In the app's own Compose file, join the network. It does not need a ports: entry: Caddy reaches it by service name.

    services:
  app:
    image: ghcr.io/you/app
    networks: [edge]

networks:
  edge:
    external: true

  3. Create your repository

    Run this on your own computer. Keep the repository private: it names your hostnames and your server.

    gh repo create my-edge --private --clone && cd my-edge
curl -sL https://github.com/pungoyal/caddy-edge/archive/refs/heads/main.tar.gz |
  tar -xz --strip-components=3 caddy-edge-main/examples/instance

  4. Tell it where your server is

    Replace the address, user and email with yours. The deploy key is created for this purpose only, and its private half goes straight into GitHub's secret store.

    gh api -X PUT "repos/{owner}/{repo}/environments/production"
gh variable set SSH_HOST --env production --body 203.0.113.10
gh variable set SSH_USER --env production --body deploy
gh variable set SSH_KNOWN_HOSTS --env production \
  --body "$(ssh-keyscan -t ed25519 203.0.113.10 2>/dev/null)"
gh variable set DEPLOY_PATH --env production --body /opt/edge
gh variable set DOCKER_NETWORK --env production --body edge
gh variable set ACME_EMAIL --env production --body you@example.com

ssh-keygen -t ed25519 -f deploy_key -C github-actions -N ""
gh secret set SSH_PRIVATE_KEY --env production < deploy_key
ssh-copy-id -f -i deploy_key.pub deploy@203.0.113.10
rm deploy_key deploy_key.pub

  5. Go live

    Point a DNS A record for your hostname at the server. Put the hostname and your app's service:port in sites/app.caddy, then push. When the run finishes, the app answers on HTTPS.

    git add -A && git commit -m "Serve my first app"
git push -u origin main
gh run watch

Is it for you?

It does one job. Here is where that job ends.

A good fit

  • A handful of apps on one server, each on its own hostname.
  • You want every change to the proxy reviewed, in git, and reversible.
  • You would rather not give a proxy access to the Docker socket.
  • You deploy your apps yourself and only need the front door.

Look elsewhere

  • You need a WAF, rate limiting or bot rules.
  • You want to hide the server behind a CDN proxy. Certificates here require the server to answer directly.
  • You run several servers behind one address.
  • You want apps to appear by container label, with no repository: use caddy-docker-proxy or Traefik.

Questions

What does it cost?

Nothing. caddy-edge is MIT licensed, Caddy is open source, certificates are free, and a deploy uses a few minutes of GitHub Actions time, well inside the free allowance for private repositories.

Do I need Cloudflare?

No. Any DNS provider works if you create the record yourself. With Cloudflare the form can create and delete records for you; they must be DNS-only, not proxied.

How do updates reach me?

Your workflows use caddy-edge at an exact commit, so nothing changes until you say so. Renovate opens a pull request when there is a new release, and merging it deploys the update.

What access does GitHub have to my server?

One SSH key for one user, held as a secret in your repository. That user can run Docker, which is equivalent to root, so anyone who can push to your repository controls the server. Keep the repository private and its collaborators few. The security policy spells this out.

Can I use Caddy features this does not mention?

Yes. A site file is plain Caddy config with two imports in it. Add redirects, basic auth, path rules or anything else Caddy supports below them.

What ends up on my server?

One directory holding compose.yaml, .env and caddy/, and one running container. No agent, no scripts, no scheduled jobs.
